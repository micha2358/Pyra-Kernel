SCOPE AND EVIDENCE
------------------
This inventory is based on the integrated source distribution
"Pyra-M4-Letux-Cleanup-Integrated-Source.zip", specifically its
provenance/changed-files.json and its complete unified source patch
patches/0001-pyra-m4-letux-preserving-cleanup-complete.patch.
The baseline is the ORIGINAL Pyra source archive with the Debian -10
distribution diff ALREADY APPLIED. Existing Pyra-specific modifications
present in that baseline are not counted as new changes.

The integrated source project verified exactly 15 changed kernel source
paths against that baseline (14 modified existing files, one new DTS).
The full unified patch is reproduced verbatim in Appendix A, so this
document covers every source-code difference, not just the highlights.

The user-provided compiled kernel archive and its installer additionally
contain boot images, modules and bootloader configuration; these are
distinguished from source changes below. A source comparison is not
equivalent to a runtime or functional validation of every subsystem.

1. EXECUTIVE SUMMARY
--------------------
The modified kernel adds experimental OMAP5432 IPU/Cortex-M4 remoteproc
support while retaining the existing Pyra Cortex-A15 Linux environment.
Its principal changes are:

  - A Device Tree-aware OMAP remoteproc driver derived from Linux v5.7.
  - A separate M4-enabled Pyra V5.3 Device Tree.
  - Remoteproc, OMAP mailbox and IPU-related configuration enabled.
  - Explicit CPU0-only M4 startup, with CPU1 held in reset.
  - Controlled IPU AMMU Small Page 0 mapping to on-chip L2 SRAM.
  - Conservative start guards, register readback, rollback and one
    firmware-start attempt per Linux kernel boot.
  - OMAP PRM reset-handling corrections, including selected Letux 7.3
    behavior and an opt-in IPU-only reset assertion quirk.
  - Targeted fixes for charger configuration, MMC timeout arithmetic,
    OMAP DMM/TILER allocation failure, and DWC3 USB/OTG state handling.
  - Small kernel build compatibility and IOMMU header adjustments.
  - A distinct kernel release name and module directory to preserve
    the original kernel as a recovery option.

The project does NOT add a general-purpose M4 DDR memory mapping,
reserved-memory/CMA pool, RPMsg application, new mailbox MMIO mapping,
or routine CPU1 execution. The presence of a remoteproc driver does
not by itself demonstrate a successful firmware boot.

2. EXACT FILE-BY-FILE SOURCE CHANGES
------------------------------------

[01] arch/arm/Makefile
  * Moves -msoft-float into the earlier ARM KBUILD_CFLAGS definition,
    so compiler feature probes and ordinary kernel C compilation both
    use the correct no-hardware-FP kernel ABI.
  * Removes the duplicate later -msoft-float occurrence.
  * This is a build-flag ordering fix, NOT an enablement of NEON in the
    kernel and NOT a change to the Pyra userspace ABI.

[02] arch/arm/boot/dts/Makefile
  * Adds omap5-letux-cortex15-v5.3+pyra-v5.3-m4test.dtb to the
    CONFIG_SOC_OMAP5 Device Tree build targets.
  * Retains the original Pyra V5.3 DTB target.

[03] arch/arm/boot/dts/omap5-letux-cortex15-v5.3+pyra-v5.3-m4test.dts
  * NEW source file (10 lines).
  * Includes the original V5.3 board DTS.
  * Overrides only the IPU node with: &ipu { status = "okay"; };
  * The original board DTS remains unmodified.

[04] arch/arm/boot/dts/omap5.dtsi
  * Adds an IPU node at physical address 0x55020000, initially disabled.
  * Compatible string: "ti,omap5-ipu".
  * Internal L2 SRAM region: 0x55020000, length 0x10000 (64 KiB);
    register name "l2ram".
  * Connects the IPU IOMMU (&mmu_ipu), two reset controls
    (&prm_core 0 and &prm_core 1), IPU clock and OMAP mailbox.
  * Firmware name: "omap5-ipu-fw.xem4".
  * No reserved-memory node or memory-region reference is added.

[05] arch/arm/configs/pyra_defconfig
  * Changes CONFIG_LOCALVERSION from "-pyradef" to "-pyradef-m4test".
  * Enables CONFIG_OMAP2PLUS_MBOX=y.
  * Enables CONFIG_REMOTEPROC=y.
  * Enables CONFIG_OMAP_REMOTEPROC=y.
  * Other defconfig lines are unchanged by the combined source patch.
  * The actual distributed build additionally supplies
    LOCALVERSION=-m4clean, producing the release string
    5.6.19-pyradef-m4test-m4clean.

[06] drivers/gpu/drm/omapdrm/omap_dmm_tiler.c
  * Sets ret = -ENOMEM if the TILER refill DMA allocation fails,
    before entering the existing error cleanup path.
  * Fixes the returned error code; it does not change the PowerVR
    rendering pipeline.

[07] drivers/iommu/omap-iommu.c
  * Adds three header includes: linux/atomic.h, linux/moduleparam.h,
    and linux/string.h.
  * No executable IOMMU function or mapping logic is changed by the
    final combined patch in this file.
  * Earlier diagnostic IOMMU experiments are NOT part of this clean
    source snapshot.

[08] drivers/mmc/host/omap_hsmmc.c
  * Casts busy_timeout to u64 before multiplying by NSEC_PER_MSEC.
  * Prevents 32-bit intermediate arithmetic overflow in the busy
    response timeout calculation.

[09] drivers/power/supply/bq2429x_charger.c
  * Removes accidental trailing semicolons from two
    of_property_read_u32() conditionals.
  * Applies precharge-current and charge-termination-current values
    only when their optional Device Tree properties were read
    successfully, rather than potentially using an uninitialized
    local value.

[10] drivers/remoteproc/Kconfig
  * Updates the OMAP remoteproc help text to mention OMAP4 and OMAP5
    Device Tree-based IPU support instead of claiming OMAP4-only
    support.
  * The actual feature selection is made in pyra_defconfig.

[11] drivers/remoteproc/omap_remoteproc.c
  * Replaces the earlier platform-data-oriented OMAP driver with a
    Device Tree-aware driver based on the Linux 5.7 implementation,
    adapted to Linux 5.6 interfaces.
  * Uses Device Tree compatible matches, firmware-name, reset
    controls, clocks, mailbox channel and optional timer resources.
  * Maps internal remote-processor memories and implements the
    remoteproc device-address-to-host-address translation callback.
  * Supports firmware loading, start/stop, mailbox signaling,
    watchdog/timer integration, runtime PM and suspend/resume paths
    where applicable.
  * Sets rproc->auto_boot = false; the M4 firmware is not started
    automatically when remoteproc registers.
  * Adapts timer set_load() to the three-argument kernel API,
    da_to_va() to an int length argument, and boot-address logging
    to a 32-bit 0x%08x format.
  * Adds the built-in module parameter
      omap_remoteproc.pyra_cpu0_only=1
    for the OMAP5 IPU. The parameter defaults to disabled.
  * When CPU0-only mode is requested, obtains two independent reset
    controls, asserts both, and verifies both are held at probe.
  * On a firmware start, reasserts CPU0 and CPU1 reset, performs
    AMMU preflight, releases CPU0 only, and verifies the expected
    post-start reset state (CPU0 released, CPU1 held).
  * Refuses an OMAP5 IPU firmware start if CPU0-only mode is not
    active; this is an experimental safety constraint, not generic
    dual-core IPU support.
  * On stop, asserts CPU0 and ensures CPU1 remains held.
  * Adds an atomic one-attempt-per-kernel-boot guard. A second
    firmware-start attempt is rejected; reboot is required.
  * Implements a guarded AMMU Small Page 0 preparation:
      - Requires CPU0-only mode and both CPU reset lines asserted.
      - Checks RM_IPU_RSTCTRL at 0x4AE06910 equals 0x00000003
        before allowing the transition.
      - Reads IPU configuration registers through the host-visible
        0x55080000 region, including Page 0 and Page 1 address,
        translation and policy registers.
      - Accepts only known Page 0 values (ADDR=0, XLTE=0 or
        0x55020000, POLICY=0x0b) and known Page 1 values
        (ADDR=0x40000000, XLTE=0x55080000, POLICY=0x09),
        together with expected MMU/cache-maintenance state.
      - If necessary, writes 0x55020000 to the Page 0 XLTE
        register at host physical address 0x550809A0, mapping
        the M4-local address 0 to the internal IPU L2 SRAM.
      - Reads back the written value and rechecks relevant
        registers and CPU reset states before CPU0 release.
      - On failed verification, attempts to restore the original
        XLTE value, keeps CPU0 in reset, and reports an error.
      - Does not write external Linux IOMMU page tables, DDR,
        CPU1 reset from the AMMU helper, or cache maintenance
        registers.
  * Retains the Letux PRM changes implemented separately in
    drivers/soc/ti/omap_prm.c; the AMMU helper does not replace
    the PRM reset driver.
  * Removes historical experimental diagnostic branches and their
    boot-argument switches from the final clean driver.

[12] drivers/remoteproc/omap_remoteproc.h
  * Updates the source header/SPDX metadata and copyright years.
  * Adds mailbox message identifiers for automatic/system suspend,
    suspend acknowledgement/cancellation, and end-of-message marker:
      RP_MBOX_SUSPEND_AUTO   = 0xFFFFFF10
      RP_MBOX_SUSPEND_SYSTEM = 0xFFFFFF11
      RP_MBOX_SUSPEND_ACK    = 0xFFFFFF12
      RP_MBOX_SUSPEND_CANCEL = 0xFFFFFF13
      RP_MBOX_END_MSG       = 0xFFFFFF14

[13] drivers/soc/ti/omap_prm.c
  * Adds the module parameter omap_prm.pyra_ipu_prm_trace,
    disabled by default, for read-only IPU CORE PRM snapshots.
  * Adds the module parameter
    omap_prm.pyra_ipu_prm_assert_quirk,
    disabled by default, for an explicitly requested IPU CORE
    reset assertion during PRM probe.
  * Restricts the optional quirk to the IPU CORE PRM instance
    (base 0x4AE06700) and rst_map_012.
  * Preserves unrelated RSTCTRL bits via read-modify-write,
    followed by a readback to flush the posted write.
  * In reset deassertion, returns early if the requested reset
    is already released.
  * After clearing a reset bit, uses
    readl_relaxed_poll_timeout_atomic() to wait for RSTCTRL
    to reflect the cleared state.
  * If a reset status register exists, additionally waits for
    the corresponding RSTST bit using atomic polling.
  * These are retained selected Letux 7.3 reset-sequencing
    corrections; they are NOT a wholesale import of Letux 7.3.
  * Optional tracing logs PWRSTCTRL, PWRSTST, RSTCTRL and RSTST
    before/after reset deassertion and at relevant probe points.

[14] drivers/usb/dwc3/dwc3-omap.c
  * Checks whether the VBUS regulator is enabled before disabling
    it when the USB ID signal floats.
  * Initializes both USB and USB_HOST extcon states, including
    explicit OFF/FLOAT states when no cable is present.
  * Uses devm_regulator_get_optional() for VBUS: tolerates
    -ENODEV but preserves other errors, including probe deferral.
  * Depopulates child devices on an IRQ setup failure before
    unwinding runtime PM.

[15] security/selinux/include/classmap.h
  * Restricts the PF_MAX compile-time address-family check to
    builds where __EXPORTED_HEADERS__ is not defined.
  * This is a header/export build-compatibility change.

3. BUILD, OUTPUTS AND INSTALLED BOOT DIFFERENCES
------------------------------------------------
These are build and installation differences, not additional
kernel source paths.

3.1 Kernel version and modules
  Original running kernel:
    5.6.19-pyradef
  Experimental built kernel:
    5.6.19-pyradef-m4test-m4clean
  New modules installed separately at:
    /lib/modules/5.6.19-pyradef-m4test-m4clean/
  The supplied staging package contains 946 .ko module files.
  The original module directory is retained.

3.2 PowerVR SGX544MP2
  The original PowerVR SGX driver source is NOT modified by this
  combined source patch. The new module tree includes the
  1.14.3699939 pvrsrvkm_omap5_sgx544_116.ko build for the new
  kernel release. The installer does not replace the native
  PowerVR EGL/GLES2 userspace libraries.
  A matching module in the archive is not by itself a guarantee
  of successful hardware operation.

3.3 Device Trees
  The original Pyra V5.3 DTB remains available.
  The experimental DTB is built from the -m4test.dts file.
  The installer can copy/rename that DTB as an -m4clean.dtb
  boot file; that installed filename does not imply a separate
  -m4clean.dts source.

3.4 Initramfs
  The new kernel uses a matching initramfs generated on the
  target system, when required by the existing boot configuration.
  The supplied kernel staging archive does not contain a
  prebuilt initramfs.

3.5 Extlinux boot entry
  The additional user.cfg entry is named "pyra-m4clean".
  In the user's displayed configuration it specifies:
    LINUX  /vmlinuz-5.6.19-pyradef-m4test-m4clean
    FDT    /dtb/linux-image-5.6.19-pyradef/
           omap5-letux-cortex15-v5.3+pyra-v5.3-m4clean.dtb
    INITRD /initrd.img-5.6.19-pyradef-m4test-m4clean
  Its APPEND line retains the original root and board boot
  parameters and adds:
    omap_remoteproc.pyra_cpu0_only=1
  The original l0, l0r and l0h entries are retained.
  Extlinux configuration is not compiled into the kernel.
  The previously shown configuration had conflicting
  "default pyra-m4clean" and "default l0" lines; this is a
  bootloader configuration issue, not a kernel source change.

3.6 Firmware
  The integrated source project includes an external firmware-v12
  test project for M4 local SRAM. That firmware is a separate
  Cortex-M4 program, NOT an alteration to Linux kernel source,
  and it is NOT bundled into the compiled kernel installer.
  The DT firmware-name property is "omap5-ipu-fw.xem4".
  Successful M4 execution on this rebuilt kernel requires a
  separate on-device verification.

4. EXPLICIT NON-CHANGES / LIMITATIONS
------------------------------------
  * No change to the baseline Pyra board DTS itself.
  * No source changes to the PowerVR SGX driver or userspace.
  * No Mesa, GL4ES or GLX replacement is introduced.
  * No extra CPU1 startup is enabled in CPU0-only mode.
  * No reserved-memory/CMA allocation for IPU firmware is added.
  * No general-purpose DDR AMMU mapping is added.
  * No new RPMsg application protocol is implemented.
  * No Phase 9.13+ mailbox IPC feature is included in this v6
    clean-kernel source snapshot.
  * No kernel-wide adoption of Letux 7.3 is implied.
  * No claim that the new kernel is already the running kernel:
    the user's earlier uname -r output was 5.6.19-pyradef.
  * Runtime tests are required for PowerVR, MMC/F2FS, USB, suspend,
    M4 startup and other hardware paths.

+ * AMMU SMALL_ADDR/XLTE/POLICY 0/1: cfg+0x920/0x9a0/0xa20 + 4*n.
+ * Thus read host-visible config at physical 0x55080920 etc.
+ *
+ * Do NOT use RSC_DEVMEM, alter AMMU entries, or modify the external IOMMU.
+ * All accesses are read-only and happen while CPU0 remains in reset.
+ * CAUTION: speculative MPU access to IPU CFG may generate an L3 error.
+ */
+/* PYRA_M4_CLEAN_LETUX_PRESERVED: OMAP5432 CPU0-only local SRAM bootstrap.
+ *
+ * Preserves the proven 9.11.5 reset/AMMU sequence and ALL external OMAP PRM
+ * backports. This helper never touches PRM reset controls, CPU1 reset,
+ * Linux IOMMU page tables, cache-maintenance registers, or DDR.
+ *
+ * The one-attempt-per-kernel-boot guard remains deliberately: safe repeatable
+ * IPU warm-reset/restart has NOT been established on the Pyra.
+ */
+static int pyra_ipu_ammu_prepare(struct device *dev,
+                                 struct omap_rproc *oproc)
+{
+    void __iomem *prm = NULL, *map = NULL;
+    u8 __iomem *cfg;
+    u32 a0, x0, p0, a1, x1, p1, mmucfg, maint, maintst;
+    u32 rb, after_rstctl, after_a0, after_p0, after_a1, after_x1;
+    u32 after_p1, after_mmucfg, after_maint, after_maintst;
+    int cpu0, cpu1, ret = -EPERM;
+    bool modified = false;
+
+    if (!oproc->cpu0_only || !oproc->cpu1_reset ||
+        !of_device_is_compatible(dev->of_node, "ti,omap5-ipu")) {
+        dev_err(dev, "PYRA-M4: CPU0-only OMAP5 IPU required\n");
+        return -EPERM;
+    }
+    if (atomic_cmpxchg(&pyra_ipu_boot_attempted, 0, 1) != 0) {
+        dev_err(dev, "PYRA-M4: repeat start blocked; reboot required\n");
+        return -EBUSY;
+    }
+
+    cpu0 = reset_control_status(oproc->reset);
+    cpu1 = reset_control_status(oproc->cpu1_reset);
+    if (cpu0 != 1 || cpu1 != 1) {
+        dev_err(dev, "PYRA-M4: CPU resets not held (%d/%d)\n",
+                cpu0, cpu1);
+        return -EPERM;
+    }
+
+    /* TI OMAP5432 TRM SWPU249AG, RM_IPU_RSTCTRL at 0x4AE06910.
+     * 0x3 means MMU/cache released but both M4 CPUs still held.
+     */
+    prm = ioremap(0x4ae06910, 4);
+    if (!prm)
+        return -ENOMEM;
+    if (readl(prm) != 0x00000003) {
+        dev_err(dev, "PYRA-M4: IPU PRM reset sequence not ready\n");
+        goto out;
+    }
+
+    map = ioremap(0x55080000, 0x1000);
+    if (!map) {
+        ret = -ENOMEM;
+        goto out;
+    }
+    cfg = (u8 __iomem *)map;
+    a0 = readl(cfg + 0x920);
+    x0 = readl(cfg + 0x9a0);
+    p0 = readl(cfg + 0xa20);
+    a1 = readl(cfg + 0x924);
+    x1 = readl(cfg + 0x9a4);
+    p1 = readl(cfg + 0xa24);
+    maint = readl(cfg + 0xca8);
+    maintst = readl(cfg + 0xcb4);
+    mmucfg = readl(cfg + 0xcb8);
+
+    /* Two accepted inputs: observed Pyra state x0=0 or already-correct
+     * TI target x0=0x55020000. Unknown policies are NOT guessed at.
+     * This is a proven SRAM-only configuration, not a general DDR mapping.
+     */
+    if (a0 != 0 || (x0 != 0 && x0 != 0x55020000) || p0 != 0x0b ||
+        a1 != 0x40000000 || x1 != 0x55080000 || p1 != 0x09 ||
+        mmucfg != 0 || maint != 0 || maintst != 0) {
+        dev_err(dev, "PYRA-M4: unknown IPU AMMU configuration; no start\n");
+        goto out;
+    }
+
+    if (x0 != 0x55020000) {
+        wmb();
+        writel(0x55020000, cfg + 0x9a0);
+        modified = true;
+    }
+    rb = readl(cfg + 0x9a0);
+    after_a0 = readl(cfg + 0x920);
+    after_p0 = readl(cfg + 0xa20);
+    after_a1 = readl(cfg + 0x924);
+    after_x1 = readl(cfg + 0x9a4);
+    after_p1 = readl(cfg + 0xa24);
+    after_mmucfg = readl(cfg + 0xcb8);
+    after_maint = readl(cfg + 0xca8);
+    after_maintst = readl(cfg + 0xcb4);
+    after_rstctl = readl(prm);
+    cpu0 = reset_control_status(oproc->reset);
+    cpu1 = reset_control_status(oproc->cpu1_reset);
+    mb();
+
+    if (rb != 0x55020000 || after_a0 != a0 || after_p0 != p0 ||
+        after_a1 != a1 || after_x1 != x1 || after_p1 != p1 ||
+        after_mmucfg != mmucfg || after_maint != maint ||
+        after_maintst != maintst || after_rstctl != 0x3 ||
+        cpu0 != 1 || cpu1 != 1) {
+        dev_err(dev, "PYRA-M4: AMMU verification failed; CPU0 held\n");
+        ret = -EIO;
+        if (modified) {
+            writel(x0, cfg + 0x9a0);
+            rb = readl(cfg + 0x9a0);
+            mb();
+            if (rb != x0)
+                dev_err(dev,
+                        "PYRA-M4: AMMU rollback FAILED; full reboot required\n");
+        }
+        goto out;
+    }
+    dev_info(dev, "PYRA-M4: SRAM AMMU ready, CPU0 release permitted, CPU1 held\n");
+    ret = 0;
+out:
+    if (map)
+        iounmap(map);
+    if (prm)
+        iounmap(prm);
+    return ret;
+}

+/* 1 sec is long enough time to let the remoteproc side suspend the device */
+#define DEF_SUSPEND_TIMEOUT 1000
+static int _omap_rproc_suspend(struct rproc *rproc, bool auto_suspend)
+{
+	struct device *dev = rproc->dev.parent;
+	struct omap_rproc *oproc = rproc->priv;
+	unsigned long to = msecs_to_jiffies(DEF_SUSPEND_TIMEOUT);
+	unsigned long ta = jiffies + to;
+	u32 suspend_msg = auto_suspend ?
+				RP_MBOX_SUSPEND_AUTO : RP_MBOX_SUSPEND_SYSTEM;
+	int ret;
+
+	reinit_completion(&oproc->pm_comp);
+	oproc->suspend_acked = false;
+	ret = mbox_send_message(oproc->mbox, (void *)suspend_msg);
+	if (ret < 0) {
+		dev_err(dev, "PM mbox_send_message failed: %d\n", ret);
+		return ret;
+	}
+
+	ret = wait_for_completion_timeout(&oproc->pm_comp, to);
+	if (!oproc->suspend_acked)
+		return -EBUSY;
+
+	/*
+	 * The remoteproc side is returning the ACK message before saving the
+	 * context, because the context saving is performed within a SYS/BIOS
+	 * function, and it cannot have any inter-dependencies against the IPC
+	 * layer. Also, as the SYS/BIOS needs to preserve properly the processor
+	 * register set, sending this ACK or signalling the completion of the
+	 * context save through a shared memory variable can never be the
+	 * absolute last thing to be executed on the remoteproc side, and the
+	 * MPU cannot use the ACK message as a sync point to put the remoteproc
+	 * into reset. The only way to ensure that the remote processor has
+	 * completed saving the context is to check that the module has reached
+	 * STANDBY state (after saving the context, the SYS/BIOS executes the
+	 * appropriate target-specific WFI instruction causing the module to
+	 * enter STANDBY).
+	 */
+	while (!_is_rproc_in_standby(oproc)) {
+		if (time_after(jiffies, ta))
+			return -ETIME;
+		schedule();
+	}
+
+	ret = reset_control_assert(oproc->reset);
+	if (ret) {
+		dev_err(dev, "reset assert during suspend failed %d\n", ret);

+	}
